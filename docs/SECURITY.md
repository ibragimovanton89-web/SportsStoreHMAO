# Безопасность
## Реализовано
- HTTPS redirect; HSTS за пределами Development.
- Antiforgery middleware. Будущие формы изменения состояния должны сохранять проверку токенов; GET не должен менять данные.
- Identity с EF Core store, пароль от 12 символов, минимум 4 различных символа, стандартные требования регистра/цифр/символов, уникальный email, подтверждённый email, блокировка после 5 ошибок на 15 минут. Миграции создают роли Admin/Manager/Customer, но не пользователей с паролями.
- Cookie: __Host- prefix, Secure, HttpOnly, SameSite=Lax, 30 минут без sliding expiration.
- CSP: same-origin ресурсы, запрет iframe, объектов и внешних форм; nosniff, referrer и permissions policies.
- Razor экранирует обычный текст; не использовать MarkupString для пользовательского ввода.
- SQL параметры обеспечиваются EF Core; sensitive data logging выключен, исключения в Production не показывают стек.
- Нет платёжных форм, аналитики, внешних шрифтов и публичной регистрации покупателей. Служебные аккаунты и необходимые сведения существующих покупателей доступны сотрудникам с подходящими правами.
- Секреты не включены в файлы проекта. Production требует явную конфигурацию.
- Закупочный прайс отделён от собственного каталога и продажных цен. Preview не меняет действующие предложения; Apply транзакционен, сериализован по поставщику и проверяет ревизию/дату. SQL-параметры используются для внешних данных.
- ExcelDataReader читает сохранённые значения, не исполняет макросы или формулы. Есть ограничения размера файла, числа строк/колонок и длины текста.
- Оптовая цена определяется сервером по сохранённому статусу Approved, не по роли сотрудника или выбору клиента. Ручные цены защищены от автоматического пересчёта.
- PostgreSQL подключается через отдельную роль sportsstore без SUPERUSER/CREATEDB/CREATEROLE. .env и резервные копии исключены из Git.
- Локальная SportsStore.Tools предназначена для доверенного оператора с доступом к БД; это не публичный API. Не передавать в QuoteAsync произвольный userId из запроса — только ID текущего аутентифицированного пользователя.

Главная страница SSR, административные маршруты — Interactive Server и AuthorizeRouteView. Inline import map отсутствует. CSP сохранена без unsafe-inline; WebSocket разрешён только текущему хосту. Для размещения настройте точный AllowedHosts.

Реализованы серверные policies, стандартные Identity TOTP/recovery codes, rate limit входа, antiforgery HTTP-формы, проверка stamp активного circuit и атомарный аудит. Claim MFA сохраняется при обновлении проверенной cookie. Bootstrap требует скрытый ввод пароля и локальное подтверждение; приглашения используют стандартные одноразовые токены. Матрица — [admin-permissions.md](admin-permissions.md).

XLS до 10 МиБ временно хранится вне wwwroot и удаляется после обработки. Фотографии до 5 МиБ/16 Мп декодируются SkiaSharp и перекодируются в WebP без исходных метаданных. SVG и скачивания произвольных URL нет.

## До открытия аккаунтов
1. Для будущих покупательских операций добавить проверку принадлежности заказов и адресов. Полномочия сотрудников уже отделены от коммерческого сегмента.
2. Подключить реальную почту и полноценное восстановление доступа. Сейчас есть ручные приглашения сотрудникам и резервные коды MFA; публичного сброса пароля нет.
3. При расширении Blazor сохранять действующие проверки stamp и текущих ролей; не доверять данным о полномочиях из браузера.
4. Определить минимальный набор персональных данных, сроки хранения, удаление/обезличивание, разграничение доступа и обработку обращений. Подготовить политику обработки данных и необходимые согласия с профильным специалистом до сбора данных.
5. Разместить данные и резервные копии согласно применимым требованиям после правовой проверки. Этот документ — инженерный план, а не подтверждение юридического соответствия.
6. Шифровать диски, резервные копии и чувствительные поля, хранить ключи отдельно с ротацией. Ограничить доступ к production и проверить восстановление резервных копий.
7. Сохранять Data Protection keys в защищённом постоянном хранилище, шифровать at rest; общий key ring для нескольких экземпляров. Иначе перезапуски/переключение узлов могут инвалидировать cookie и токены.
8. За reverse proxy настроить ForwardedHeaders только от доверенных прокси перед HTTPS redirect; настроить точный AllowedHosts. Установить TLS-сертификат и безопасные лимиты запросов.
9. Логи не должны содержать пароли, токены, строки подключения, адреса и платёжные данные. Аудит значимых операций отделить от технических журналов, задать сроки хранения и доступ.
10. Обновить пакеты до актуальных исправлений, выполнить dotnet list package --vulnerable --include-transitive, интеграционные проверки БД, авторизации, CSRF, rate limits и тесты безопасности.

## До подключения оплаты
- Использовать платёжного провайдера с размещённой у него платёжной страницей. Не принимать и не хранить PAN/CVV.
- Итоговую сумму, валюту, скидки и доступность товара рассчитывать на сервере.
- Проверять подпись webhook, сумму, валюту и идентификатор платежа. Защищать обработку от повторов; переходы статусов выполнять атомарно и идемпотентно.
- Не считать возврат браузера с платёжной страницы доказательством оплаты.
- Возвраты и изменение реквизитов защитить отдельными правами и аудитом; предусмотреть сверку и процедуру расследования расхождений.
- Для опта определить роли согласования и неизменяемую историю документов. Условия госзакупок и фискализации согласовать перед реализацией.

## Закупочный этап

Передача поставщику, приёмка, пороги и публикация цен требуют Admin на сервере. Количества, версия заказа и цены проверяются повторно в транзакции; итог из браузера не принимается. Приёмка не отправляет внешних сообщений и не инициирует платежей. Закупочные заказы отделены от заказов покупателей. Публичная витрина получает отдельные DTO без закупочных цен; фотографии скрытых карточек требуют Staff и выдаются без длительного кеширования.

## Локальный тестовый вход — временное исключение

По запросу владельца включён `Development:BypassAdminAuthentication` в конфигурации Development. `DevelopmentAdminAccess.ValidateEnvironment` останавливает запуск с включённым флагом в любой другой среде. Middleware после обычной аутентификации создаёт отдельную серверную личность только для loopback-клиента и локального Host; клиентские claims и заголовки не включают этот режим.

Привилегии привязаны к закрытому типу ClaimsIdentity в памяти, а не к передаваемому claim или имени схемы. Cookie для тестового входа не выдаётся. Политики SSR, Blazor, серверные сервисы и перепроверка circuit распознают эту личность; операции попадают в аудит с ActorId `local-development-admin`. Анти-CSRF, валидация и ограничения БД действуют. Тестовый вход не предназначен для проверки реальных паролей, MFA и приглашений: для этих сценариев установите флаг в false и перезапустите процесс.

Не выставляйте Development-хост наружу через localhost-прокси/туннель: такой прокси может скрыть происхождение запроса. Production должен запускаться с выключенным флагом. Для возврата авторизации установите false в appsettings.Development.json либо Development__BypassAdminAuthentication=false, затем перезапустите приложение; открытые тестовые circuits завершатся вместе с процессом.
