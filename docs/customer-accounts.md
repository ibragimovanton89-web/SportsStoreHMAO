# Аккаунты покупателей

Четвёртый этап использует существующий ASP.NET Core Identity со строковым ключом пользователя. Новых таблиц паролей нет. `Customer.ApplicationUserId` остаётся необязательной уникальной связью. Старые покупатели не присваиваются зарегистрировавшемуся пользователю по совпадению имени, почты или ИНН.

## Маршруты

| Маршрут | Назначение |
| --- | --- |
| `/customer/register` | Регистрация нового покупателя |
| `/customer/login` | Вход подтверждённого покупателя |
| `/customer/confirm-email?userId=…&token=…` | Просмотр ссылки и подтверждение отдельным POST |
| `/customer/resend-confirmation` | Повторное письмо подтверждения |
| `/customer/forgot-password` | Запрос восстановления |
| `/customer/reset-password?userId=…&token=…` | Смена пароля по одноразовому коду |
| `/customer/profile` | Имя, телефон, правовой тип и реквизиты |
| `/customer/addresses` | Собственные адреса: добавление, изменение, удаление |
| `/customer/wholesale` | Заявки, снимки реквизитов и публичная история решений |
| `/customer/security` | Смена пароля с проверкой текущего |
| `/customer/logout` | Только POST с antiforgery; GET возвращает 405 |

Razor Pages выбраны для форм, меняющих cookie: HTTP-ответ ещё доступен, в отличие от события действующего Blazor circuit. Формы используют `ICustomerAccount`; они не принимают CustomerId для выбора владельца, ApplicationUserId, Segment, WholesaleStatus или роли. Подставленные поля не влияют на серверную команду. Возврат после входа допускается только на локальные адреса каталога/кабинета.

## Регистрация и вход

`CustomerRegistration` создаёт отдельную DI-область. `UserManager` и `ApplicationDbContext` разрешаются в ней совместно, поэтому пользователь, роль Customer и профиль сохраняются одной транзакцией. PostgreSQL advisory lock по нормализованной почте сериализует повторную регистрацию. Уникальное имя Identity и уникальная связь покупателя дополнительно защищают данные. Ошибка создания профиля откатывает пользователя и роль.

Новый покупатель — физлицо, Retail, NotRequested; почта первоначально не подтверждена. Существующие записи по почте не связываются. Пароль: минимум 12 символов, минимум четыре разных символа, прописная/строчная буква, цифра и специальный символ. Identity блокирует вход после пяти неудачных попыток на 15 минут. Почта должна быть подтверждена до входа. Cookie имеет `Secure`, `HttpOnly`, `SameSite=Lax`, префикс `__Host-`, срок 30 минут без скользящего продления.

Вход сотрудника остаётся `/account/login` с обязательной MFA. Покупательская форма не обслуживает Admin/Manager. Роль сотрудника не означает скидку, а локальный admin bypass не создаёт покупателя.

## Защита сессии и данных

`CustomerAccess` при каждой операции проверяет пользователя, подтверждение почты, security stamp, блокировку и связь покупателя. Если у связанного пользователя появились полномочия сотрудника, требуется также MFA. Идентификатор адреса/заявки проверяется вместе с владельцем; чужая запись не раскрывается.

Общий `StaffAuthenticationStateProvider` теперь перепроверяет учётную запись независимо от роли каждые 15 секунд. Проверка Staff остаётся отдельной и требует текущих ролей/MFA. Прикладные команды не ждут фоновой перепроверки. Смена/восстановление пароля обновляет stamp; остальные cookie и circuits утрачивают доступ. Собственная сессия после обычной смены пароля обновляется.

Телефон хранится только в `AspNetUsers.PhoneNumber` и помечается неподтверждённым. Почта из профиля не редактируется. Существенные реквизиты — Kind, LegalName, Inn, Kpp. Их изменение при Approved или Pending требует явного согласия на отзыв условий/заявки. Телефон, имя и адрес не отзывают опт.

Профиль и адреса защищены `xmin`; устаревшая форма не перезаписывает чужое изменение. При конфликте введённые поля остаются в форме, пользователю предлагается скопировать их и обновить данные.

Все POST используют antiforgery. Чувствительные POST ограничены по IP; регистрация/письма/вход дополнительно ограничены по HMAC нормализованной почты в ограниченном процессе кэше. Для нескольких экземпляров приложения необходим общий распределённый ограничитель. Страницы кабинета и каталога возвращают `private, no-store`; token-страницы имеют `no-referrer`. Стандартное журналирование полного URL отключено. Не включайте логирование тел форм или query string на обратном прокси.

## Следующий этап

`ICustomerAccount`, `CustomerAccess`, проверенный Customer и `IPricingService` можно использовать как основу корзины и заказа. Чтение кабинета и цены не создаёт заказ, резерв, оплату или обещание доставки. Перед публичным запуском владелец настраивает SMTP, домен, хранение ключей, юридические тексты и политику работы с персональными данными.

## Локальный вход при включённом обходе Admin

Тестовый обход применяется только к анонимному локальному запросу. После входа покупателя или сотрудника настоящая Identity-cookie имеет приоритет и не заменяется локальным Admin. Поэтому покупатель остаётся покупателем и не получает административные права. Для отдельной гостевой проверки по-прежнему отключайте bypass в проверочном процессе.
